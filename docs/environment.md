# Environment variables

GENERATED by `npm run docs:env` from `SPEC` and `lib/env-registry.mjs`. Do not edit by hand.

Every variable this project reads is listed here. `test/env.inventory.test.mjs` scans the source
and fails if a variable is read without being declared, or declared without being read — so this
document cannot quietly fall behind the code.

One setting has no variable: `version`, which describes the file it appears in rather than
overriding behaviour.

A `string[]` variable is comma-separated. A boolean accepts `1/true/yes/on` and `0/false/no/off`.
An invalid value falls back to the default and is reported by `npm run doctor` rather than throwing.

**No setting variable holds a secret.** `CMR_WORKER_API_KEY_ENV` sets the NAME of the variable that
holds the key, never the key.

## Everything else

These are not settings, which is why they are declared in `lib/env-registry.mjs` rather than in
`SPEC`: a secret whose variable name is itself configurable, a path the host supplies, a kill
switch, a test channel. Putting them in `SPEC` would make the config loader claim to own values it
does not.

### Credentials

Never stored in configuration, never written to a telemetry row, and never printed. Doctor reports only presence, length and a four-character prefix, which is what makes its output safe to paste into an issue.

| Variable | Required | Secret | Default | Subsystem | Purpose |
| --- | --- | --- | --- | --- | --- |
| `GEMINI_API_KEY` | only when a lane resolves to the gemini provider | **yes** | — | providers | The Gemini API key. Read at call time and never stored in config; doctor reports only its presence, length and first four characters. |

**`GEMINI_API_KEY`** — THE NAME IS NOT FIXED. `worker.apiKeyEnv` and `workers.<lane>.apiKeyEnv` make it a config value, so the set of credential variables this project may read is open-ended by design. This entry documents the default, and the test pins the MECHANISM rather than the name.

### Supplied by Claude Code

Set by the host for a hook or a command. The code treats every one of these as optional and falls back, because a hook that threw on a missing variable would break the session it was meant to help.

| Variable | Required | Secret | Default | Subsystem | Purpose |
| --- | --- | --- | --- | --- | --- |
| `CLAUDE_PROJECT_DIR` | no | no | `process.cwd()` | config, hook | The project root, used to locate <project>/.claude/model-router.json and to resolve a read path against the project rather than the process working directory. |
| `CLAUDE_PLUGIN_ROOT` | yes, for the hook to run at all | no | — | hook | The installed plugin directory. Substituted by Claude Code into the hook command in hooks.json, which is the only supported way to name the hook script. |
| `CLAUDE_SESSION_ID` | no | no | `a per-process fallback id` | telemetry | Identifies the session a telemetry row belongs to, so delegations can be grouped by session without storing anything about its content. |

**`CLAUDE_PLUGIN_ROOT`** — Never read through `process.env` by us. Doctor reconstructs the same path from its own location and checks that the substitution would resolve to a file that exists, because a hook script Claude Code cannot find is the failure mode with no symptom.

**`CLAUDE_SESSION_ID`** — Whether Claude Code sets this for a hook process is not something this project can assert, so the code treats absence as normal and falls back rather than failing.

### Side channels

Deliberately without a `SPEC` entry. A switch that can only be reached by editing a file is not an emergency stop.

| Variable | Required | Secret | Default | Subsystem | Purpose |
| --- | --- | --- | --- | --- | --- |
| `CLAUDE_ROUTER_TELEMETRY` | no | no | — | telemetry | Kill switch for the telemetry write path. Set it to 0/false/off to stop rows being written without touching configuration. |

**`CLAUDE_ROUTER_TELEMETRY`** — Deliberately has no SPEC entry: it is an emergency stop, and a setting that can only be reached by editing a file is not an emergency stop. A test pins that exactly one module reads it.

### Operating system and Node

Supplied by the platform. Listed because the test harness sets them explicitly to isolate a child process from the developer’s real home directory.

| Variable | Required | Secret | Default | Subsystem | Purpose |
| --- | --- | --- | --- | --- | --- |
| `HOME` | no | no | — | config | The home directory, which is where the per-developer config and the default telemetry and governance directories live. |
| `USERPROFILE` | no | no | — | config | The Windows home directory. The counterpart to HOME. |
| `PATH` | yes, for any spawned child | no | — | test harness | Passed through to spawned child processes so the Node executable can be found. |
| `SystemRoot` | yes on Windows, for any spawned child | no | — | test harness | Required for a Node child process to start on Windows, so it is forwarded explicitly. |
| `TEMP` | no | no | `os.tmpdir()` | evals | Scratch directory for corpus generation. |

**`HOME`** — Named here because the test harness sets it to redirect a child away from the developer’s real ~/.claude. On Windows os.homedir() reads USERPROFILE instead, so both must be set to isolate a child on either platform.

**`SystemRoot`** — The reason the test helpers CONSTRUCT a child environment rather than spreading process.env: a constructed environment proves the child inherited nothing from the developer, but it has to carry the handful of variables without which Node will not launch.

### Internal and test-only

Read only by the test harness or the mock provider. None of these affects a real delegation.

| Variable | Required | Secret | Default | Subsystem | Purpose |
| --- | --- | --- | --- | --- | --- |
| `MOCK_WORKER_URL` | only when the mock provider is selected | no | — | providers | Base URL for the mock provider, which is how the evals and several tests run a full dispatch offline and keyless against a loopback server. |
| `MOCK_SCENARIO` | no | no | — | providers | Selects a canned mock-provider behaviour (a refusal, a timeout, a malformed usage block) so failure paths can be driven without a live provider. |
| `CMR_TEST_WRITER` | no | no | — | test harness | Payload for the JSONL writer child, which proves concurrent appends stay intact under real contention from separate processes. |
| `CMR_TEST_BUDGET_WRITER` | no | no | — | test harness | Payload for the budget ledger child, which proves the exclusive-create lock serialises mutations across processes. |

**`CMR_TEST_WRITER`** — CMR_-prefixed but NOT a setting: it carries a test payload, not configuration, and has no SPEC entry.

**`ROUTER_PERF_FULL`** — This is the one deliberately skipped test in the suite.

## What a static scan cannot see

The conformance test reads the source and matches `process.env.X`, `process.env["X"]`, `env.X` and
`env["X"]`. Four things are genuinely beyond it, and are stated here rather than implied:

1. **A computed name.** `worker.apiKeyEnv` makes the set of credential variables open-ended by
   design, so the test pins the read SITES instead of the names. Those sites are:

   - `plugins/model-router/lib/config.mjs` — Walks SPEC and reads `env[spec.env]` for each setting, plus the derived CLAUDE_PLUGIN_OPTION_<FIELD> name. Both names come from SPEC, so they are documented by the generated reference rather than here.
   - `plugins/model-router/lib/providers/contract.mjs` — Checks each name in a provider’s `requiresEnv` list to decide readiness. The list belongs to the provider module.
   - `plugins/model-router/lib/providers/gemini.mjs` — Reads the key from whichever variable `apiKeyEnv` names, which is a config value.
   - `plugins/model-router/lib/providers/index.mjs` — Resolves readiness for a provider by the same configurable key name.
   - `plugins/model-router/scripts/doctor.mjs` — Reports presence of whichever key variable each lane actually wants, which is why it can catch a key that is set but empty or unexpanded.

2. **Anything a child process reads.** The report generator forwards its environment to the
   analytics CLI it spawns, and the hook inherits whatever Claude Code gave it.
3. **Anything Node itself reads**, such as `NODE_OPTIONS`, `TZ`, or the home-directory variables
   consulted by `os.homedir()`.
4. **Whether a declared purpose is true.** Only the name set and the read sites are machine
   checkable; the meaning in these tables is prose, and prose is reviewed, not verified.
